# Windows 内置 USB 驱动管理设计（已确认）

## 目标

让 Windows 用户在 ZzRkDevTool 内完成板卡的 WinUSB 驱动安装或替换，无需额外下载 Zadig。已有 WinUSB 的设备直接使用；已有瑞芯微驱动的设备由用户主动选择切换，不在启动、插拔或烧录时自动修改驱动。

用户期望保留恢复瑞芯微工具使用环境的途径。恢复能力必须按实际保存的驱动包验证，不能把“备份成功”视为“恢复一定成功”。

## 已确认的依据

- 当前 Windows `probe` 在 `libusb_open` 返回 `LIBUSB_ERROR_NOT_SUPPORTED (-12)`，用户的原厂烧录工具可以工作；具体绑定服务仍需在 Windows 上确认。
- 当前传输层使用 libusb，未实现原厂 RockUSB 驱动访问后端。
- [libwdi 上游](https://github.com/pbatard/libwdi) 提供设备枚举、WinUSB 驱动包准备和安装接口，支持管理员提权。
- 上游头文件采用 LGPL-3.0-or-later；Zadig 应用本身与 libwdi 的许可证不同。本方案不嵌入 Zadig 应用。
- `wdi_device_info` 包含设备标识和驱动服务名；公开 API 提供 `wdi_prepare_driver`、`wdi_install_driver`，不提供通用原厂驱动恢复接口。
- libwdi 可以生成目录文件及自签名证书。此机制不等同于项目已有可信生产签名，也不能保证通过所有企业策略或 Windows 安全策略。

## 方案选择

推荐使用 libwdi DLL 和独立的 Windows 驱动管理辅助进程。主程序提供现有风格的界面，辅助进程只在执行驱动变更时申请管理员权限。

备选一是分发 Zadig 应用，但会引入第二套界面及 GPL 应用分发要求。备选二是完全自研 INF、安装和签名流程，维护成本更高，暂不采用。

## 页面与操作

入口放在 Windows 的“设备”页，针对状态栏选中的设备提供“驱动管理”。Linux 和 macOS 不显示此入口。

驱动管理界面显示设备名称、端口路径、实例 ID、硬件 ID、接口号、驱动服务、提供商和版本。操作提供“切换为 WinUSB”和“恢复原驱动”；只有找到可验证的恢复记录时才允许恢复。

确认页明确列出驱动替换的影响：原厂 RK 工具可能暂时不可用，相同硬件 ID 的设备可能受影响。选择一个端口不代表 Windows 驱动绑定必然只影响这一块板卡。

首版安装前枚举所有已连接 USB 实例，拒绝存在另一块相同硬件 ID 的板卡，避免只备份目标实例却替换另一台的驱动。复合父节点还根据 USB 配置/设备描述符独立过滤，不只判断服务名。

只允许操作项目已支持的 Rockchip 设备及目标接口，禁止操作 Hub、复合父设备或任意其他 USB 设备。已绑定 WinUSB 时不重复安装。

## 安装与恢复流程

1. 检查没有烧录、擦除、备份或其他设备任务，重新确认设备身份与当前驱动。
2. 记录当前驱动包、硬件与接口标识，调用 Windows 系统接口或工具导出可用的原始驱动包，生成恢复记录。
3. 已有第三方驱动而备份无法完成时，中止替换并说明原因。原本没有驱动的设备记录为无原始驱动。
4. 展示影响范围，由用户确认后启动提权辅助进程。
5. 使用 libwdi 准备和安装 WinUSB 包，保留系统要求的授权和证书提示，不关闭驱动签名校验。
6. 等待设备重新枚举，检查绑定服务，再执行只打开、声明和释放接口的 probe。安装程序返回成功不等于设备已可使用。
7. 恢复时核对保存的驱动包和目标，使用 Windows 驱动安装接口完成重新绑定；不把单纯添加驱动包视为恢复完成，也不删除可能被其他设备使用的共享驱动包。
8. 若需要重新插拔或重启，明确显示该状态，不报告已恢复或已就绪。

原厂绑定确认包含当前 INF 与可信原包内容核对；安装后检查设备启动/问题状态和重启标志。恢复成功后提示用原厂工具验证，不对原厂驱动运行仅适用于兼容驱动的 libusb probe。

## 模块边界

- Windows 驱动信息查询：负责将 libusb 端口和 Windows 设备实例关联，查询服务及驱动包信息。
- 驱动管理服务：负责操作状态、设备复核、备份记录、恢复协调和结果反馈。
- 提权辅助进程：负责受限的安装与恢复请求，不接受任意命令、硬件 ID 或外部 DLL 路径。
- GUI：负责展示、确认、进度和结果，不直接调用底层安装 API。
- 现有 libusb 传输层：继续负责实际 USB 通信，不承担驱动安装。

安装期间释放本程序的设备句柄，并阻止启动新的设备任务；安装结束后刷新状态栏设备信息。记录中区分 libwdi、Windows 安装错误和 libusb probe 错误。

## 依赖、构建与分发

libwdi 只参与 Windows 构建，优先动态链接。实施前固定并验证一个上游稳定版本，检查对应的 MSVC 构建、内嵌资源和辅助程序要求，不直接追踪 master。

Windows 包内包含运行所需 DLL、辅助程序、许可证和对应版本源码获取信息，满足 LGPL 的适用分发要求。DLL 从可信的应用目录加载。Linux、macOS 不引入这些运行依赖。

更新当前 `packaging/windows/README.md` 中“驱动安装不属于应用操作”的既有策略，明确改为用户主动触发的功能。生产签名与 libwdi 自签名机制分别记录。

## 验证与验收

无硬件测试覆盖：设备匹配、操作禁用状态、权限取消、备份失败、安装失败、设备消失、超时、恢复记录失效以及同硬件 ID 影响提示。

Windows 实机按以下顺序验收：查询驱动 → 备份原驱动 → 切换 WinUSB → probe → 只读信息 → Loader/Maskrom 重新枚举 → 完整升级与回读 → 恢复原驱动 → 原厂工具重新识别。切换过程中重新枚举的设备身份分别检查，不假定只安装一次就覆盖所有阶段。

还需验证两块同型号板卡、UAC 取消、中文路径和 Windows 安全策略导致安装失败的行为。实机验证完成前，不标注为 Windows 驱动切换已支持。

## 实施顺序

先完成 Windows 驱动查询、备份能力及 libwdi 构建验证；随后增加 WinUSB 安装、probe 与恢复闭环；最后接入 GUI、打包与测试说明。恢复闭环未验证前，不对用户发布一键双向切换功能。
